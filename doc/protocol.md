# HDMIブリッジ プロトコル仕様

送信側(本体Pico/Pico W等)と受信側(このファームウェアを書き込んだPico 2)の
間で、SPI1(マスター)→SPI0(スレーブ)経由でやり取りするワイヤプロトコルの
完全な仕様。実装は`main.c`、送信側の実装例は
[../../PB-1000_emu_AG2/src/lcd_controller.c](../../PB-1000_emu_AG2/src/lcd_controller.c)
（`lcd_send_hdmi_*()`系関数）を参照。

## 設計方針

送信側ごとに固定の解像度・拡大率・ビット深度をファームウェアへ埋め込むのでは
なく、**パケットヘッダーに毎回自己記述させる**ことで、受信側ファームウェアを
完全に汎用化している。これにより:

- 送信元プロジェクトが変わっても(例: MSXエミュレータ ⇔ PB-1000エミュレータ)、
  受信側の書き込み直しが不要
- 送信側Pico2を電源を入れたまま挿し替えても追従する(ホットスワップ対応、
  [architecture.md](architecture.md)参照)
- 送信元の解像度が実行中に変化しても(例: PB-1000の32/64ドット切替)追従する

## 物理層

1回のCS Low区間 = 1パケット = **8byteヘッダー + ペイロード**。

- SPIモード3(CPOL=1, CPHA=1)必須。RP2350のPL022 SPIスレーブ実装はモード0
  (CPOL=0/CPHA=0)だと数byte受信後に同期が崩れる既知の制約があるため
  ([hardware_guide.md](hardware_guide.md)参照)。
- ボーレートは任意(実機検証済み: 10MHz)。送信側の`spi_set_baudrate()`で
  設定する値がそのまま使われる — 受信側は`spi_init(spi0, 30MHz)`で上限だけ
  設定しており、実際のクロックは常にマスター(送信側)が決める。
- バイトオーダーはMSB first。マルチバイトの数値フィールド(width/height等)は
  すべてbig-endian。

## ヘッダー共通レイアウト(8byte)

```
オフセット  0        1        2    3    4    5    6        7
フィールド  pkt_type (種別依存: 下記参照)
```

`[0]`のパケット種別によって`[1]`〜`[7]`の意味が変わる。

## パケット種別一覧

| 値 | 名前 | 用途 |
|---|---|---|
| `0x00` | `PKT_PALETTE` | パレット更新 |
| `0x01` | `PKT_FRAME` | ピクセルフレーム(ゲーム画面等) |
| `0x02` | `PKT_TEXT_CMDS` | 文字コマンド列(メニュー等の大きいUI) |
| `0x03` | `PKT_BEZEL_CMDS` | 文字コマンド列(ベゼル等、ゲーム画面と重なる装飾) |
| `0x04` | `PKT_CLEAR_SCREEN` | 画面全体クリア + 追跡状態リセット |
| それ以外 | (未知) | `PKT_FRAME`として前方互換的に解釈される |

以下、各種別のヘッダー`[1]`〜`[7]`とペイロードの詳細。

---

### `PKT_PALETTE` (0x00)

```
[0] = 0x00
[1] = エントリ数 (0は256として扱う。256を超える値は256に丸められる)
[2]〜[7] = 未使用(0推奨)
ペイロード = エントリ数 byte、各1byte = RGB332
```

直近に受信したパレットは、以後の`PKT_FRAME`(bpp<8時)・`PKT_TEXT_CMDS`・
`PKT_BEZEL_CMDS`で参照され続ける。パレット自体を毎フレーム送る必要はない
(内容が変わらない限り一度だけ送れば十分)。

**例**: 16色パレット(インデックス0=黒, 1=白のみ設定する場合)

```
ヘッダー: 00 10 00 00 00 00 00 00        (種別=PALETTE, エントリ数=16)
ペイロード: 00 FF 00 00 00 00 00 00 00 00 00 00 00 00 00 00
            (idx0=0x00黒, idx1=0xFF白, idx2-15=0x00)
```

---

### `PKT_FRAME` (0x01)

```
[0] = 0x01
[1] = bpp (1/2/4/8。それ以外の値は8として扱われる)
[2],[3] = width  (uint16, big-endian)。0または MAX_IMG_W(256) 超過は256に丸め
[4],[5] = height (uint16, big-endian)。0または MAX_IMG_H(192) 超過は192に丸め
[6] = scale (整数拡大率。0は1として扱う。MAX_SCALE(4)超過は4に丸め、さらに
      width*scale/height*scaleが画面(640x480)に収まるよう自動で減らされる)
[7] = 予約(0)
ペイロード = width * height * bpp / 8 byte (行優先)
```

- **bpp=8**: 1byte/pixelがそのまま RGB332(パレット参照なし、直接色)。
- **bpp=1/2/4**: 1byteに `8/bpp` pixel分のパレット番号をMSB詰めで格納する。
  例えばbpp=4なら、1byte中の上位nibbleが行内で先に来るpixel、下位nibbleが
  次のpixelのパレット番号(0〜15)。直近の`PKT_PALETTE`の内容を参照して
  RGB332へ変換される。
- 1行のバイト数は `width * bpp / 8`。端数が出ないよう、`width`は`8/bpp`の
  倍数であることが送信側の責務(例: bpp=4なら widthは2の倍数)。

**例**: 4x2のbpp=8フレーム(拡大率2倍)

```
ヘッダー: 01 08 00 04 00 02 02 00
          (種別=FRAME, bpp=8, width=4, height=2, scale=2)
ペイロード(8byte、RGB332直接、行優先):
  行0: E0 1C 03 FF   (赤 緑 青 白)
  行1: 00 00 00 00   (黒4つ)
```

**例**: 4x2のbpp=4フレーム(パレット参照、拡大率1倍)

```
ヘッダー: 01 04 00 04 00 02 01 00
          (種別=FRAME, bpp=4, width=4, height=2, scale=1)
ペイロード(4byte、1byteに2pixel、MSB詰め):
  行0: 0x12 0x34   -> pixel(0,0)=idx1, (1,0)=idx2, (2,0)=idx3, (3,0)=idx4
  行1: 0x00 0x00   -> 全てidx0
```

---

### `PKT_TEXT_CMDS` (0x02) / `PKT_BEZEL_CMDS` (0x03)

ヘッダー・ペイロード書式は完全に同一。**種別だけが異なり**、受信側は
ウィンドウ中央寄せの最大サイズ追跡(後述の「表示ウィンドウの中央寄せ」参照)を
この2種別で独立させる。

```
[0] = 0x02 (PKT_TEXT_CMDS) または 0x03 (PKT_BEZEL_CMDS)
[1] = payload_len の上位byte
[2],[3] = width  (uint16, big-endian) — 論理キャンバス幅(センタリング用)
[4],[5] = height (uint16, big-endian) — 論理キャンバス高さ
[6] = scale
[7] = payload_len の下位byte
ペイロード = payload_len byte のコマンド列
```

- `width`/`height`は実際のピクセルデータではなく、後続のコマンド内の座標が
  属する「論理キャンバス」のサイズ — ウィンドウの中央寄せ計算にのみ使われる。
  0は1に、640/480超過はそれぞれ640/480に丸められる。
- `payload_len`は`MAX_PAYLOAD`(49,152byte)を超える場合は丸められる。実際に
  送るコマンド列がこれを超えないようにするのは送信側の責務。1画面分は通常
  でも高々数百byte程度で収まる。

ペイロードは以下2種類のコマンドを任意個並べたバイト列。**先頭から順に解釈し、
末尾まで処理する**。未知のコマンドIDに遭遇した場合はコマンド境界を見失って
いる可能性があるため、安全側に倒してそこで処理を打ち切る(以降は無視)。

#### `CMD_RECT` (0x00) — 10byte(先頭のコマンドID byte込み)

```
[0] = 0x00
[1],[2] = x (uint16, big-endian、論理キャンバス座標)
[3],[4] = y (uint16, big-endian)
[5],[6] = w (uint16, big-endian)
[7],[8] = h (uint16, big-endian)
[9] = color (RGB332)
```

キャンバス座標`(x, y)`から`w × h`の矩形をcolorで塗る。

#### `CMD_TEXT` (0x01) — 8 + str_len byte(先頭のコマンドID byte込み)

```
[0] = 0x01
[1],[2] = x (uint16, big-endian、文字列開始位置)
[3],[4] = y (uint16, big-endian)
[5] = fg (前景色, RGB332)
[6] = bg (背景色, RGB332)
[7] = str_len (文字数、0〜255)
[8..] = 文字コード列 (str_len byte、ASCII)
```

各文字コードを`font_petme128_8x8[]`(MicroPython本体の`framebuf`モジュールと
同一フォント、MIT license)で8x8展開し、x方向へ`8 * scale`pixelずつ進めながら
順に描画する。文字コードは32(スペース)〜127(DEL)の範囲。範囲外の値は
MicroPython本体の`framebuf.text()`と同じ挙動で127番(市松模様)にフォール
バックする。

**例**: `(x=4, y=4)`に白文字"Hi"を黒背景で描画するコマンド

```
01 00 04 00 04 FF 00 02 48 69
(CMD_TEXT, x=4, y=4, fg=白(0xFF), bg=黒(0x00), str_len=2, "Hi"=0x48,0x69)
```

これに、背景クリア用の矩形コマンドを前に置いた完全なペイロード例
(320x240キャンバス、拡大率2倍):

```
ヘッダー: 02 00 01 40 00 F0 02 14
          (種別=TEXT_CMDS, payload_len=20, width=320, height=240, scale=2)
ペイロード(20byte):
  00 00 00 00 00 01 40 00 F0 00     (CMD_RECT: (0,0)-(320,240)を黒で全面クリア。10byte)
  01 00 04 00 04 FF 00 02 48 69     (CMD_TEXT: 上記の"Hi"。10byte)
```

(ヘッダー`[1]`=payload_len上位byte=0x00, `[7]`=下位byte=0x14 → 0x0014=20。
CMD_RECTが10byte、CMD_TEXTが8+2=10byteで合計20byte。)

---

### `PKT_CLEAR_SCREEN` (0x04)

```
[0] = 0x04
[1]〜[7] = 未使用(0推奨)
ペイロード = ダミー1byte(内容は無視される)
```

画面全体(640x480)を黒でクリアし、全種別(`KIND_PIXEL`/`KIND_TEXT`/
`KIND_BEZEL`)の中央寄せ追跡状態(後述)を完全にリセットする。送信側の
本体Pico2が再起動された直後など、受信側(電源が入ったまま)に前セッションの
表示が残っている状況をクリアするために使う。送信側は起動処理の最初、HDMI
初期化が完了した直後に送るのが典型的な使い方。

**なぜ専用パケットなのか**: `PKT_TEXT_CMDS`等で640x480の黒矩形を送る方式に
すると、その`KIND`自体の最大サイズ追跡が640x480に膨らんでしまい、以後その
種別で送られる本来小さいフレームのウィンドウが誤ったサイズで中央寄せされて
しまう(実際に起きた不具合)。`PKT_CLEAR_SCREEN`はどの`KIND`の追跡にも一切
影響を与えない、完全に独立した操作として設計されている。

---

## 表示ウィンドウの中央寄せ

受信側は、`PKT_FRAME`/`PKT_TEXT_CMDS`/`PKT_BEZEL_CMDS`をそれぞれ独立した
「種別」(`KIND_PIXEL`/`KIND_TEXT`/`KIND_BEZEL`)として扱い、**種別ごとに
「これまで受信した最大のwidth/height」を覚えておき、それを基準に画面
(640x480)の中央へウィンドウを固定する**。

```
win_w = (この種別の最大width) * scale   (画面幅を超える場合は画面幅にクランプ)
win_h = (この種別の最大height) * scale  (画面高さを超える場合は画面高さにクランプ)
left_margin = (640 - win_w) / 2
top_margin  = (480 - win_h) / 2
```

- 最大値は**増える方向にしか更新されない**。送信元の解像度が縮んだ場合
  (例: PB-1000の64→32ドット切替)でも、ウィンドウ自体は最大時のサイズの
  ままなので画面上での位置が動かない — 空いた分は黒でクリアされる。
- **種別ごとに独立している**のが重要な点。もし全種別で単一の追跡変数を
  共有すると、一度でも大きいコンテンツ(例: `PKT_TEXT_CMDS`のメニュー画面、
  480x320)が来た後に小さいコンテンツ(例: `PKT_FRAME`のゲーム画面、
  192x64)が来ると、後者のウィンドウが前者の大きさに引きずられて画面
  左上に寄ってしまう不具合が実際に起きた。3種別(`KIND_PIXEL`/`KIND_TEXT`/
  `KIND_BEZEL`)は互いに重なって共存しうる別々のレイヤーとして扱われ、
  各レイヤーは自分自身の直前の描画領域だけを黒でクリアしてから次を描く。
- `PKT_BEZEL_CMDS`は、`PKT_FRAME`(ゲーム画面)と**全く同じ論理座標系・
  scale**で送ることで、独立して中央寄せされつつも結果的に画面上で
  ゲーム画面を対称に一回り包む位置に重なるよう設計されている(送信側の
  実装例は`_draw_bezel_hdmi()`を参照)。

## 実装上の制約(定数)

| 定数 | 値 | 意味 |
|---|---|---|
| `SCREEN_W` / `SCREEN_H` | 640 / 480 | HDMI出力解像度(固定、640x480@60Hz) |
| `MAX_IMG_W` / `MAX_IMG_H` | 256 / 192 | `PKT_FRAME`のwidth/height上限(超過はクランプ) |
| `MAX_SCALE` | 4 | scaleフィールドの上限(超過はクランプ) |
| `MAX_PAYLOAD` | 49,152 byte | 受信バッファ1面分のサイズ。`PKT_FRAME`のbpp=8時の最大ペイロード(256×192)から算出。`PKT_TEXT_CMDS`/`PKT_BEZEL_CMDS`のpayload_lenもこの範囲に丸められる(送信側は超えないこと) |
| `MAX_PALETTE_ENTRIES` | 256 | パレットエントリ数の上限 |

`PKT_TEXT_CMDS`/`PKT_BEZEL_CMDS`のwidth/heightは`MAX_IMG_W`/`MAX_IMG_H`とは
無関係(画面サイズ640x480が上限)— 実パネル解像度(例: 480x320)をそのまま
送ってよい。ペイロード自体はコマンド列であって解像度に比例しないため、
`MAX_PAYLOAD`(受信バッファサイズ)にさえ収まればよい。

## 未定義動作・前方互換性

- 未知のパケット種別(`0x05`以上)は`PKT_FRAME`として解釈される。
- `PKT_TEXT_CMDS`/`PKT_BEZEL_CMDS`ペイロード内の未知のコマンドIDは、
  そこで処理を打ち切る(以降のバイトはコマンド境界を見失っている可能性が
  あるため解釈しない)。
- ヘッダー・ペイロードの途中で送信が途切れた場合(送信側の物理的な挿し
  抜き等)は、受信側のウォッチドッグが自動検出・復旧する。詳細は
  [architecture.md](architecture.md)参照。
